# Разработка

[Оглавление](README.md)

## Требования и запуск

Нужен Node.js 24.13+ со встроенным SQLite и npm для удобных команд. Внешние npm-зависимости отсутствуют; `npm install` для запуска не требуется. Docker Engine и Compose нужны только для контейнерной сборки и интеграционной проверки.

Команды этого раздела выполняются из полного каталога исходников, не из `dist/`.

```sh
node --version
npm start
```

Для наблюдения за файлами:

```sh
npm run dev
```

Адрес по умолчанию — `http://127.0.0.1:4173`; при занятом порте используйте `PORT=4174 npm start`. Статические файлы сервер читает при старте, поэтому обычному `npm start` после правки интерфейса нужен перезапуск.

На компьютере, где создавался проект, использовалась отдельная рабочая версия Node:

```sh
/Users/artur/.cache/codex-runtimes/codex-primary-runtime/dependencies/node/bin/node server.mjs
```

Это локальный путь конкретного окружения, не требование к другим компьютерам или VPS. Если системный Node выдаёт ошибку `simdjson` до запуска JavaScript, используйте исправную установку Node; сам сервис ещё не начал выполняться.

## Структура исходников

```text
public/                 Клиент, кабинет, сбор, сигналы и справки
server.mjs              HTTP API и lifecycle
security.mjs            Конфигурация, доверие к proxy, квоты и JSON
reports.mjs             Проверка и нормализация отчёта
database.mjs            SQLite, ключ, сессии, сохранение и поиск
connection.mjs          Серверное наблюдение и HTTP-заголовки
audit.mjs               Журнал безопасности
scripts/                Сборка, ротация, backup, healthcheck, Docker smoke
tests/                  Node test runner
deploy/Caddyfile         Публичный HTTPS и локальный административный вход
compose.yaml            App, Caddy и одноразовые инструменты
Dockerfile              Тестовая стадия и runtime
.env.example            Шаблон настроек Compose
docs/                   Документация
.data/                  Локальные данные; не часть исходников
dist/                   Генерируемый пакет; не редактировать вручную
```

## Команды

| Команда | Действие |
| --- | --- |
| `npm start` | Запуск из текущего каталога |
| `npm run dev` | Node watch |
| `npm test` | Автоматическая pretest-сборка, затем все `tests/*.test.mjs` |
| `npm run build` | Пересоздание `dist/`; каталог удаляется перед копированием |
| `npm run admin:rotate` | Новый ключ и отзыв сессий в выбранной БД |
| `npm run backup -- /absolute/path/copy.sqlite` | Проверенная онлайн-копия, существующий файл не перезаписывается |

`DATABASE_PATH` применяется к серверу, ротации и backup. Если путь относительный, он зависит от cwd. Для проверки используйте отдельную временную БД, не рабочую `.data/`.

## Добавление браузерной проверки

1. В `public/collector.js` добавьте запись в `buildProbes()` с уникальным `id`, существующей категорией и `run`, возвращающим объект значений.
2. Для отсутствующего API используйте имеющиеся `unsupported`/`unavailable` механизмы; не подменяйте отсутствие данных нормальным значением.
3. Добавьте предметные пояснения в `public/field-info.js`. Названия и значения должны оставаться данными, не HTML.
4. Проверки с разрешениями помещайте в `optionalProbes`; не вызывайте камеру, микрофон, геолокацию или доступ к устройствам из основного автоматического сбора.
5. Проверьте штатный результат, отсутствие API и отказ разрешения. Существенные преобразования и изоляцию ошибок проверяйте тестами.

`runProbe` превращает объект результата в строки `probeId.field`, нормализует значения и изолирует ошибку одной проверки. Основной сбор выполняется четырьмя задачами, обычный тайм-аут проверки — 7 секунд. Дополнительный запуск через интерфейс ожидает до 12 секунд; системный запрос разрешения зависит от браузера.

Новая категория требует согласованного изменения списка категорий клиента и разрешённых категорий в `reports.mjs`. Изменение набора данных, назначения или передачи может требовать обновления текста/версии согласия в `public/consent.js`.

## Изменение сигналов и схемы

Эвристики находятся в `public/signals.js` и импортируются сервером. Обрабатывайте только ожидаемые типы: посетитель может прислать вместо строки объект или массив. Для сигнала нужны объяснение, ложноположительные сценарии и связанные поля. Не превращайте отсутствие API или приватность в самостоятельное доказательство бота.

Формат запроса меняйте вместе с клиентом, `reports.mjs`, API/моделью данных и тестами. Существующие SQLite-данные нельзя считать автоматически мигрированными: текущий код создаёт таблицы, но не содержит полноценного migration runner. Перед изменением схемы нужен backup и проверенный порядок перехода.

Новый статический файл нужно добавить в серверный allowlist; наличие файла в `public/` само по себе не делает новый путь доступным. В production также проверьте ограничения административного origin и правила Caddy.

## Проверки

| Файл | Что проверяет |
| --- | --- |
| `tests/diagnostics.test.mjs` | Изоляция ошибок/тайм-аутов, профиль, сигналы и безопасные заголовки |
| `tests/persistence.test.mjs` | Согласие, запись, поиск, приватность, вход, CSRF, срок сессий и ротация |
| `tests/security.test.mjs` | Production через Unix socket, квоты, валидация, аудит, гонки входа и предел SQLite |
| `tests/build.test.mjs` | Наличие исполняемых частей сборки и исключение приватных данных |

Для полного прогона используйте `npm test`: тест сборки импортирует `dist/`, поэтому запуск всех тестов без предварительной сборки может проверять старый пакет. Проверки используют временные БД, loopback-порты и Unix sockets; нужны разрешённые ОС файловые операции и локальные подключения.

Контейнерная проверка:

```sh
docker build -t fingerprint-security-check:local .
node scripts/smoke-docker.mjs
```

Сборка запускает тесты внутри Linux. Smoke создаёт отдельный случайно названный Compose-проект, loopback-порты и локальный CA; проверяет TLS, изоляцию админки, вход/выход, отправку, IP и backup. После завершения удаляет только свои контейнеры, CA и volumes. Настоящий домен, ACME и рабочая база не используются.

## Сборка и поставка

`scripts/build.mjs` копирует разрешённые исходники, клиент, эксплуатационные скрипты и документацию в `dist/`, формирует минимальные npm-команды и `.gitignore`. Реальные `.data`, `.env` и ключи не копируются. В Docker тестовая стадия собирает тот же пакет, runtime получает его без тестового дерева.

Сам `dist/` не является полным Docker-проектом: для сборки образа используйте исходники с Dockerfile, Compose, тестами и `deploy/`. Для обычного локального запуска пакета:

```sh
cd dist
npm start
```

При таком запуске без абсолютного `DATABASE_PATH` появится отдельная база `dist/.data/`. После обновления процесса проверьте, что он использует нужный путь и не создал новую пустую БД из-за другого cwd.

После изменения документации проверьте внутренние ссылки и сборку. После изменения HTTP/SQLite/доверия к proxy запускайте относящиеся к нему тесты и полный прогон перед выпуском. Не включайте реальные ключи и отчёты в fixtures, логи, примеры и архивы.
